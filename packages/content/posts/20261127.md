仕事でもプライベートでも、AI にバリバリ書かせるのが当たり前になりました。  
理解を補うために、人間が理解しやすい 動画・画像・UML等の図示、自然言語のテストコード などを使うようになりました。  
以下の記事でもあるように、個人サイトのリニューアルをしていますが、その作業でも同様のことをしています。  

https://silverbirder.github.io/blog/contents/20261117/

ただ、どうしても理解を補う情報は増えても、やはり理解を深める姿勢は必要不可欠と考えています。  

## 失敗した

私が取り組んでいる個人サイトのリニューアルの話をします。  
ブログ記事（マークダウンファイル）をGitHubリポジトリ管理から、別のCMS用 GitHub リポジトリ管理に移します。  
CMSにあるブログ記事をどのようにしてサイト側へ渡すか、ビルド&デプロイフローについて考えました。  
どのようなフローで進むのか、シーケンス図を成果物としてレビューしていましたが、内部の詳細なことを知らずにそのままやってみました。  
すると、「あれ、GitHubのレートリミットに引っかかった」となってしまいました。  
GitHub API を使ってコンテンツデータを取得するのですが、一括ではなく個々の記事（500記事ほど）を取っていたためです。  
まあ言葉にすると、なんで気付けないのかと恥ずかしく思うのですが...。  
**図解は抽象的で理解しやすい** のですが、**欠落している情報がある** のです。  
（じゃあ、コードベースを詳細に図解したものを読め...と言われても）

## 質問する

私は『間違っていると分かっていてもとにかく仕様を言語化して AI に Q&A をする』ことにしました。  
どこかのだれかは、もしかしたらこういうのをQ&Aを仕組み化して、答えれるまで進めれないみたいなこともしているみたいですが、  
自主的に今は聞いています。  

「これこれ〜こうこうで、こうだよね？」ととにかく聞いています。  
間違っている場合は、ちゃんと間違っていると指摘してくれます。  
問い詰めるなどでYESマンとかにさせなければ。  

間違っている場合、理解を訂正しようとすると何度も質問を繰り返します。  
図解も入れるのですが、それでも理解が難しい場合があります。  
その場合、システムが複雑な傾向にあると思い、私はその仕組みを見直すことが多いです。  
例えば分岐や前提条件が複雑だったりすると、そのシステムを扱う人（私）が苦しむためです。  
結果、**理解が追いつく範囲のシステムにダウン** して、それを私が運用する、となっています。笑
